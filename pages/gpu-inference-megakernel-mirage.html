一句话主线

LLM 的 decode 阶段是纯粹的显存带宽问题——GPU 99% 的算力闲着，唯一的硬约束是「把权重从显存读一遍要多久」。所有低延迟优化的本质，都是不让显存带宽出现空档。而传统「一个算子一个 kernel」的范式，恰恰在 kernel 边界上制造了大量空档。MegaKernel 就是把这些边界全部拆掉。

一、硬件地图：一条越往里越快、越往里越小的带宽阶梯

要理解 GPU 推理，先建立一张物理图景：数据从哪来、经过哪些管道、最后在哪被算。下面这张图按带宽编码横条宽度（对数尺度），纵向是「离计算单元的距离」。

CPU 是发牌员，不是搬运工

这是最容易被误解的一点。推理过程中 CPU 根本不碰模型数据。

  • 模型权重在服务启动时一次性经 PCIe 搬进显存，之后再也不动；
  • KV cache 全程在显存里分配、读写、回收；
  • 每个 decode step，PCIe 上真正往返的只有 token id 和调度元数据——几十字节到几 KB。

CPU 每一步只做两件事：① 决定这一步跑哪些请求、算好 block table 等元数据（这就是 vLLM 的 scheduler）；② 往 GPU 的命令队列里写 kernel launch 命令。

📌
记住这个角色分工

CPU 是发牌员，GPU 是牌桌。牌桌再快，发牌员发慢了，GPU 一样得饿着。后面 MegaKernel 的全部动机，就是「发牌太慢、而且每发一张牌都要全桌停一次」。

二、计算单元：CUDA Core 与 Tensor Core 到底是什么

GPU 的算力不是一坨均质的东西。一个 SM（Streaming Multiprocessor，流多处理器）内部有两类完全不同的计算单元，擅长的事情、峰值算力差 16 倍。先看解剖图。

CUDA Core：标量流水线，什么都能干

CUDA Core 就是一条标量 ALU 流水线。一个周期做一次 FP32 的乘加（FMA）＝ 2 FLOP。它的执行模型是 SIMT：32 个线程编成一个 warp，锁步执行同一条指令，每个线程占一条 CUDA Core 通道。

它是通用的——分支、地址计算、按元素的加减乘除、比较、特殊函数，统统靠它。在 LLM 推理里，这些活全是 CUDA Core 干的：

CUDA Core 的日常

RMSNorm / LayerNorm 的求和与开方 · Softmax 的 max-reduce 与 exp · RoPE 的旋转 · SiLU/GeLU 激活 · residual 相加 · 采样与 argmax · 所有的地址计算与循环控制

A100 的 FP32 峰值：6912 core × 2 FLOP × 1.41 GHz ≈ 19.5 TFLOPS。

Tensor Core：矩阵乘专用单元，一条指令吞一整块

Tensor Core 只干一件事：小矩阵的乘加 D = A × B + C。在 Ampere 上，一条 mma.sync PTX 指令由整个 warp 协作发出，一次吃掉一块 m16n8k16 的 tile。

关键问题是：为什么它能比 CUDA Core 快 16 倍？答案不是「晶体管堆得多」，而是 操作数复用。

这一节是理解后面所有内容的钥匙。把「CPU 发出一个 kernel 到它彻底结束」的全过程，摊在一条时间轴上。

1. tail effect：假设一个 kernel 切成 300 个 CTA 丢给 108 个 SM，那就是 3 轮——前两轮满载，第三轮只有 84 个 CTA，24 个 SM 完全空转。而且要等最慢的 CTA 收工。

四、Roofline：为什么 decode 是 memory-bound

现在把前两节合起来算一笔账。核心概念叫 算术强度（arithmetic intensity）：从显存搬进来的每 1 个字节，能撑起多少次浮点运算。

ridge point · 芯片的平衡点
\[ \frac{312\ \text{TFLOPS}}{1.55\ \text{TB/s}} \approx 200\ \text{FLOP} / \text{Byte} \]

意思是：从 HBM 搬 1 个字节进来，必须至少做 200 次浮点运算，才配得上这块芯片。低于这个数，Tensor Core 就在等米下锅。

算一笔账：Qwen3-8B 在 A100 上的物理下界

batch=1 的 decode，每生成一个 token 要把全部权重从 HBM 读一遍，而每个权重只参与一次乘加（2 FLOP）。所以算术强度 ≈ 2 FLOP/Byte——是 ridge point 的 1%。

下界 = 权重字节数 ÷ 显存带宽
\[ \frac{8.2\times10^9 \times 2\ \text{Byte}}{1.55\times10^{12}\ \text{Byte/s}} \;=\; \frac{16.4\ \text{GB}}{1.55\ \text{TB/s}} \;\approx\; \mathbf{10.5\ ms\ /\ token} \]

这个 10.5 ms 与你的 kernel 写得多好无关，是物理定律。MPK 博客里那句「理论下界 10 ms」就是这么来的。

🎯
于是低延迟推理的命题被彻底改写

问题不是「怎么算得更快」——算力过剩 99%。问题是：怎么让显存带宽从头到尾一秒都不闲着，把实测延迟压到 10.5 ms 这个下界上。

算力涨得比带宽快，decode 阶段的算力浪费只会越来越严重。同时 kernel 的绝对执行时间在缩短，而 launch 开销基本不变——固定开销的相对占比逐代升高。这两条趋势加在一起，就是 MegaKernel 这类工作出现的时代背景。

五、kernel-per-operator 范式交的三笔税

vLLM、SGLang、TensorRT-LLM 都遵循同一个范式：一个算子 = 一个 kernel。MPK 论文实测：Qwen3-8B 每生成一个 token，要发 293 次 kernel launch。

税 1 · launch 开销（CPU 侧）

模式单次 launch（B200 实测）× 293 次 = 每 token占 10 ms 预算
eager3.8 μs1.1 ms11%
CUDA Graph0.8 μs0.2 ms2%
MPK megakernel—（只发 1 次）≈ 0片上调度仅占总运行时 0.28%

税 2 · kernel 边界 = 全局屏障 → tail effect

就是图 5 里那条红色虚线。293 个 kernel，就是 293 次「所有 SM 必须清空、对齐、重来」。CUDA Graph 完全治不了这条——它消掉的只是 CPU 侧的发牌开销，GPU 侧的屏障一个不少。

税 3 · 跨 kernel 无法重叠（最贵的一笔）

  • 计算 ↔ 访存不能重叠。RMSNorm 在跑的时候，下一个 Linear 的权重本来完全可以提前从 HBM 预取——但那个 kernel 还没被 launch，硬件无从知晓。于是唯一的瓶颈资源（显存带宽）在这段时间是闲着的。
  • 计算 ↔ 通信不能重叠。TP 多卡时 matmul → all-reduce。实际上 all-reduce 的每一块数据只依赖 matmul 输出的一部分，算完一块就能发一块。但 kernel 粒度下，必须等整个 matmul 结束。

六、Mirage 是什么：一个仓库，两代系统

mirage-project/mirage 里其实是两代系统，共用一个代码库，容易混淆，先分清楚。

第一代 · Mirage 多级超优化器（OSDI'25）

核心表示是 μGraph——把 GPU 程序统一描述在三个层次上，每层对应一级存储：

μGraph 层次对应硬件数据放在
Kernel level整个 GPU（grid）HBM
Block level单个 SM（CTA）Shared Memory
Thread level单个 thread寄存器

它做的是超优化（superoptimization）：不靠人写重写规则，而是在 μGraph 空间里搜索语义等价但更快的实现，自动发现 FlashAttention 这类「人类专家才想得出」的融合方案，最后 transpile 成 CUDA / Triton。

搜出来的候选怎么保证正确？靠概率等价性验证——用随机指纹在有限域上比对，比形式化验证快几个数量级，同时给出极高的正确性置信度：

mirage-project/mirage · include/mirage/search/verification/probabilistic_verifier.h 
class ProbabilisticVerifier : public Verifier {
public:
  ProbabilisticVerifier(kernel::Graph const &input_graph);
  virtual OutputMatch verify(kernel::Graph const &graph) override;
private:
  std::vector<cpu::CTensor> input_graph_fingerprints;   // 输入图的指纹
};

旁边的 formal_verifier.h 是形式化验证那条路。这一代解决的是「单个 kernel 怎么写得最快」。

第二代 · MPK，Mirage Persistent Kernel（OSDI'26）

把 GPU 从「CUDA runtime 按 kernel 调度」，改成「一个驻留在 GPU 上的自定义运行时按 task 调度」。

命题变了：不再是优化单个 kernel，而是 整个模型的 forward 只发一次 kernel launch。

6.3 贯穿两代的设计哲学

两代系统看起来做的是完全不同的事，但方法论是同一条。把它抽出来，比记住任何实现细节都有用：

🧭
第一原则：找到「抽象层次」与「硬件真实层次」之间的错配，把抽象降到硬件那一层

错配一旦消除，原本「不可能」的优化会自己浮现出来——不是想出来的，是让它变得可表达。

原本的抽象硬件的真实层次降下去之后解锁了什么
第一代
μGraph		GPU 程序 = kernel 调用序列，kernel 内部是黑盒grid / block / thread 三级并行，对应 HBM / SMEM / 寄存器三级存储「这个 reduction 放 block 级还是 thread 级」变成可搜索的选择，于是能自动搜出 FlashAttention 这类融合
第二代
tGraph		调度单位 = kernel，依赖只能按整个算子记真正的调度单位是 CTA → SM依赖精确到 tile，于是跨层流水、计算通信重叠成为可能

第二原则：用搜索代替规则。传统编译器靠人写重写规则，覆盖面受限于人的想象力。Mirage 直接在 μGraph 空间里搜——而敢放开搜索空间的前提，是有一个足够快的正确性验证器，这就是概率等价验证存在的理由。验证器的速度决定了搜索空间的大小，这两件事是绑在一起设计的。

第三原则（MPK 特有）：把调度权从驱动手里夺回来，自己写运行时。只要还是「CPU 发 kernel、驱动分派 CTA」，kernel 边界就永远在那儿。MPK 的做法是启动一个永不退出的 kernel，在它内部实现一套任务队列 + 事件系统——GPU 从「被驱动调度的执行器」变成了「自己调度自己的处理器」。

下面两节就是这第三条原则的展开：先讲清楚 barrier 到底是什么，再看 MPK 怎么把它消掉。

七、barrier 到底是什么

前面反复说「293 次隐式全局 barrier」，但没说清 barrier 究竟是什么、为什么非它不可。这一节补上——不理解 barrier 为什么存在，就无法理解 MPK 为什么能拆掉它。

7.1 GPU 上有三种 barrier，层次完全不同

「CTA 之间不能互相等」这句话抽象，把它摊到泳道上就一目了然了。关键在于 CTA 的数量通常远大于 SM 的数量——它们是分批上场的。

💡
换个角度理解这张图

死锁的成因不是「CTA 会等待」，而是 CTA 在等待时仍然占着它的 SM 不放。操作系统里线程阻塞会让出 CPU，而 CTA 一旦上了 SM 就绑死到退出为止，没有抢占、没有让出。这正是 GPU 与 CPU 在调度模型上最本质的差别，也是 persistent kernel 这类技巧存在的根源。

7.2 关键认知：barrier 同时提供了两样东西

这是理解 MPK 的钥匙。一次 kernel 边界的全局 barrier，实际上一口气给了你两个保证，而人们通常只想到第一个：

保证含义MPK 用什么替代
① 执行序
execution order		第 N+1 层的任何工作，都在第 N 层全部完成之后才开始event 计数器——把「全等」换成「偏序」
② 内存序
memory ordering		第 N 层写进 HBM 的数据，第 N+1 层读得到（缓存已刷新、写已可见）acquire / release 原子操作——精确重建，且只在真正相关的两个 task 之间
⚠️
很多人只拆了①，然后踩坑

「不就是把 kernel 融合起来吗」——如果只保证执行顺序而忘了内存序，程序会在大多数时候是对的、偶尔算错，而且随 GPU 型号和负载变化。这是最难调的一类 bug。MPK 把两件事分别用不同机制重建，下一节能在源码里看得很清楚。

7.3 barrier 的三笔代价

代价一

收敛代价

必须等最慢的那个 CTA。300 个 CTA 丢给 108 个 SM＝3 轮，最后一轮只有 84 个在干活，24 个 SM 纯空转。这就是 tail effect。

代价二

清空代价

所有 SM 的流水线要排空，寄存器与 shared memory 要释放、下个 kernel 重新分配。已经在 SMEM 里的数据全部作废，下个 kernel 得重新从 HBM 搬。

代价三 · 最贵

信息代价

barrier 抹掉了细粒度依赖信息。第 N+1 层某个 tile 其实只依赖第 N 层的几个 tile，但 barrier 强制它等全部——本来能重叠的全被串行化了。

前两笔是常数开销，第三笔是结构性损失：它让「跨层软件流水」「计算与通信重叠」这类优化从一开始就无从谈起。MPK 的收益大头来自第三笔，而不是前两笔。这也解释了为什么 CUDA Graph（只压缩了 launch 开销）拿不到这部分收益。

编译期做四件事：算子拆 task（按输出张量切分）→ 依赖分析插 event → event 融合（触发同一组消费者的 event 合并、依赖同一组生产者的 event 合并，压缩同步开销）→ 图归一化 + BFS 线性化，让运行时能紧凑存储、顺序扫描。

8.2 从模型到「一次 launch」：完整编译链路

🚫
先纠正一个很自然但错误的直觉

MPK 并不是「把 CUDA Graph 转换成一个 kernel」——它根本不接触 CUDA Graph。

两者是从同一个计算图出发的两条分叉的下降路径，不是先后关系。CUDA Graph 是驱动层的对象（一张 kernel launch 的 DAG），MPK 从来不消费它；MPK 直接从计算图降到自己的 task/event 表。

两张「图」在结构上到底差在哪

🔎
一个容易被略过、但很能说明设计的细节

EventDesc 里存后继 task 的方式不是一个列表，而是 first_task_id / last_task_id 两个整数——它假定「一个 event 要放出的所有 task 在数组里是连续的」。编译期那步「BFS 线性化」就是为了让这个假设成立。用一次排序换掉了运行时的指针追逐，这在 GPU 上是很划算的交易。

对着源码走一遍这条链路

CUDA Graph 把执行计划交给 driver 保管，GPU 只能被动等着被喂；MPK 把执行计划做成 HBM 里的普通数组，于是 persistent_kernel 里的 worker 和 scheduler 能像读任何一个张量那样读它——读得到，才谈得上自己调度。

换句话说：不是「把 293 个 kernel 合并成 1 个」，而是把「293 个 kernel」这个概念整个换成了「一张写在显存里的任务表 + 一个会读表的解释器」。那个解释器就是常驻的 megakernel。

那么，什么样的算子会被融进同一个 task？

看 TaskType 枚举就能读出规律——有些算子被合并进一条记录，有些反而被拆成两条：

枚举值发生了什么
TASK_RMS_NORM_LINEAR合并：RMSNorm ＋ Linear 进同一个 task
TASK_SILU_MUL_LINEAR_WITH_RESIDUAL合并：SiLU ＋ 逐元素乘 ＋ Linear ＋ residual 加法，四个算子一条记录

TASK_PAGED_ATTENTION_SPLIT_KV_* / ..._MERGE_*拆开：split-KV attention ＋ 一个专门的 merge task

分界线只有一条：中间结果能不能一直待在这一个 CTA 的 shared memory 里，不回 HBM。

能融合

消费者只读生产者的同一块 tile

norm 的缩放系数、激活、residual 加法、紧随其后的 GEMM —— 数据从头到尾在 SMEM 和寄存器里流转。看 norm_linear.cuh：norm 权重、reduction 结果、MMA 中间量、输出全部挤在同一个 extern __shared__ char smem[] 里，靠手工分配偏移共存。RMSNorm 的结果一次都没落过 HBM。

必须拆开

需要跨 CTA 归约

全局 argmax、split-KV attention 的 softmax 分母、多卡 all-reduce —— 一个 task 就是一个 CTA，CTA 之间只能通过 HBM + event 通信。所以只能切成 partial ＋ reduce 两个 task。merge_splitkv.cuh 的注释写得很直白：它吃的是上一个 split-kv task 的输出和那个 log-exp-sum。

📏
所以 task 的边界不是「算子边界」，而是「一个 CTA 的能力边界」

能在一个 CTA 的 shared memory 预算内跑完的连续算子链，就压成一个 task；一旦需要和别的 CTA 交换数据，就必须断开、过 HBM、插一个 event。MPK 的融合能力上限，等于一个 CTA 的 shared memory 大小。

8.6 它到底怎么做到「全程没有 barrier」

回到第七节的两个保证。MPK 拆 barrier 分四步走，缺一步都不成立：

第一步 · 让所有 CTA 同时驻留，解除死锁前提

第七节说过，grid 级 barrier 之所以只能靠 kernel 边界，是因为 CTA 之间没有前向进展保证——你等的那个 CTA 可能还没被调度上 SM。

MPK 把这个前提直接掀了：让 grid 大小恰好等于物理 SM 数，且每个 SM 只放一个 CTA。所有 CTA 从头到尾同时在跑，谁等谁都不会死锁。

mirage-project/mirage · include/mirage/persistent_kernel/persistent_kernel.cuh:787-798 
__device__ __forceinline__ void persistent_checker(RuntimeConfig config) {
  ...
  // 每个 worker SM 跑一个 worker；每个 scheduler SM 塞四个 scheduler
  assert(gridDim.x ==
         config.num_workers + num_schedulers / num_schedulers_per_sm);
}

这个 assert 是正确性前提，不是性能调优。README 里 num_workers=96, num_local_schedulers=48 恰好凑成 A100 的 108，填错了不是慢一点，是直接死锁。

共驻留靠三件事一起保证：

  • __launch_bounds__(WORKER_NUM_THREADS, 1) —— 第二个参数是「每 SM 最少驻留几个 block」，写 1 就是告诉编译器按 1 CTA/SM 分配资源；
  • 把 shared memory 吃干净：runtime_header.h 里 A100 分支申请 160 KB 动态 SMEM（SM 上限 164 KB）——物理上就塞不下第二个 CTA；
  • grid 大小由上面的 assert 卡死。
📌
注意它没有用官方的 cooperative launch

CUDA 其实提供了 cudaLaunchCooperativeKernel + grid.sync() 来做合法的 grid 级同步。MPK 没用——它用的是普通 <<<>>> 启动，靠 occupancy 工程手工保证共驻留。原因很直接：grid.sync() 本身还是一个全局 barrier，那就白干了。MPK 要的不是「合法的 barrier」，是根本不要 barrier。

第二步 · 执行序：把「全等」换成「偏序」

barrier 的语义是所有人到齐；MPK 换成我等的那几个人到齐。载体就是 EventDesc.num_triggers：

语义替换

barrier：第 N+1 层所有 task　⟵ 等 ⟶　第 N 层全部 task（全等，一刀切）
event：某个下游 task　⟵ 等 ⟶　它真正读到的那 num_triggers 个上游 task（偏序）

于是第 N 层某个 tile 一算完，只依赖它的第 N+1 层 task 立刻就能上 SM——不必等同层的其他 tile。这就是跨层软件流水的全部来源，也正是第七节说的「第三笔代价」被追回来的地方。

第三步 · 内存序：用 acquire / release 精确重建

这是最容易被忽略、也最见功力的一步。没有了 kernel 边界，谁来保证生产者写的数据消费者读得到？

答案是整个 mpk_atoms.cuh——这个文件只做一件事：定义一组带 scope 的 acquire/release PTX 原语。

「消掉 barrier」不是把它删了，而是把它替换成了同样严格、但作用域小得多的东西。

第四步 · 跨迭代：连「清零」都不需要全局同步

还剩最后一个坑：一个 decode step 结束后，几百个 event 计数器得清零才能进入下一步——而「所有人都清零完了」本身就需要一次全局 barrier，兜了一圈又回去了。

MPK 的解法很漂亮：计数器根本不清零，改成把阈值乘以轮次。

mirage-project/mirage · persistent_kernel.cuh:1033-1034 
if ((count + 1) == num_triggers * get_task_iteration_num(task_ids[queue_pos])) {
  // 第 N 轮的判定阈值就是 N × num_triggers —— 计数器一路单调递增，永不 reset
}

一个乘法换掉一次全局同步。这类细节才是「全程无 barrier」能真正成立的原因——只要有任何一处还需要「所有人到齐」，前面三步的努力就全废了。

诚实的说明：不是「零同步」，是「零全局 barrier」

⚠️
CTA 内部的 __syncthreads() 一个没少

翻 execute_worker 就能看到满屏的 __syncthreads()——加载 TaskDesc 之后、执行 task 之后都有。MPK 消掉的是第七节图里的第③级（grid 级），保留了第②级（block 级）。

这个保留是对的：block 级 barrier 只有几十个周期，作用域是一个 SM 内部，既不涉及 tail effect 也不需要刷全局缓存。拿它开刀没有收益，只有风险。

8.9 代价：把一切塞进一个 kernel，要付什么

前面讲的都是收益。但「只有一个 kernel」这件事本身会带来一批结构性的约束——它们不是工程没做完，而是这条路线自带的。

① 所有 task 被迫共用同一套资源配置

这是最根本的一条。一个 kernel 只有一组编译参数，于是四百多种 task 全部挤在同一个模子里：

被锁死的东西源码后果
blockDimWORKER_NUM_THREADS ＝ 128（Ampere）/ 256（Hopper·Blackwell），编译期常量每个 task 都必须用这个线程数。一个天然适合 64 线程的小 task，和一个想要 512 线程的 GEMM，只能各自将就
shared memoryMAX_DYNAMIC_SHARED_MEMORY_SIZE（A100 上约 160 KB）按最胖的那个 task 申请，其余 task 也占着同样的额度
寄存器数__launch_bounds__(WORKER_NUM_THREADS, 1)寄存器压力最大的 task 决定全局分配；它一旦 spill，所有 task 陪着一起慢

⚖️
这是一笔真实的交易，不是纯赚

传统范式里，每个 kernel 都可以为自己挑最优的 blockDim、寄存器数、SMEM 用量——这正是 kernel 边界带来的好处之一。MegaKernel 拆掉边界的同时，也放弃了这份「每个算子各自调优」的自由。收益（消掉 barrier）必须大过这笔损失，整件事才划算。

🤔
那为什么 batch size 能分桶，seq 长度却只能锁一个上限？

因为两者的数据形态根本不同：

· batch size 是整步的一个标量——一次 decode step 只有一个 batch 值，所以「编译期生成多份 tGraph、运行时选一份」是成立的。

· seq 长度是每个请求各不相同的——同一步里四个请求可能是 100 / 5000 / 200 / 30000。根本不存在一个能代表这一步的 seq 值，也就无从选桶。

要分桶就得逐请求分桶，而一张静态图里每个请求槽位的 task 是固定的，于是只能退化成：给每个槽位按最坏情况配满 chunk task。这就是「锁上限」而不是「分桶」的由来。

代价是实打实的：序列远短于设计点时，多数 chunk task 分到的 KV 区间是空的，白占 SM；而要提高上限，得改宏、重新编译。

🔁
和 vLLM 对照，这里有个反转

前面说过，vLLM 要发明 piecewise、要给 attention backend 做四级兼容性分级，都是因为 attention 不 graph-safe——看起来是个丑陋的妥协。

但正是这个妥协，让 vLLM 在 seq 维度上完全自由：attention 压根没进 CUDA Graph，长度随便变。MPK 把 attention 也收编成 task（更优雅，也确实换来了跨层流水），代价就是把 seq 长度一起静态化了。

同一笔交易的两面：你把什么纳入静态图，就得为它的动态性付静态化的代价。

③ 生态：不能调用任何现成的 kernel

cuBLAS、cuDNN、FlashAttention、FlashInfer、CUTLASS 的成品 kernel 全都是 __global__ 函数——它们是「一个 kernel」，而 MPK 需要的是「能在 kernel 内部被调用的 __device__ 函数」。

所以 MPK 把所有算子重写了一遍，这就是 TaskType 长到四百多项的原因。代价是：

  • 白名单制——枚举里没有的算子就是没有。新模型架构出现时，vLLM 可能当天就能跑，MPK 要等有人写 task。
  • 吃不到上游红利——FlashAttention 出了新版本、CUTLASS 出了新 GEMM 内核，MPK 都无法直接受益。
  • 正确性负担全在自己身上——每个重写的算子都要自己保证数值正确，而这些库是被全世界验证过的。

④ 可观测性：profiler 只看得见一个 kernel

Nsight Compute / nsys 的核心抽象就是 kernel：kernel 级的耗时排序、occupancy 分析、访存分析——在 megakernel 面前全部失效，因为整个 forward 只有一个 kernel，你只会看到「它跑了 12.5 ms」。

MPK 的应对是自建：RuntimeConfig 里有个 profiler_buffer，task 执行前后写时间戳（PROFILER_EVENT_START/END），事后导出成 Perfetto trace。这等于自己重建了一套 profiler——能用，但和成熟工具链的差距是实打实的。

⑤ 一处崩溃 = 整个 kernel 挂掉

没有 kernel 边界，也就没有了天然的故障隔离点。任何一个 task 越界写、死循环、或 assert 失败，整个常驻 kernel 一起完蛋；而它常驻的特性又意味着「重启」等于重新初始化全部状态。加上参数填错会直接死锁（第七节），排障难度和传统范式不是一个量级。

⑥ 编译产物与指令 cache

四百多种 task 的代码全部链进同一个 kernel，二进制体积和编译时间都显著增长；运行时每个 SM 的 L1 指令 cache 也要装下当前执行的各类 task 代码，存在 i-cache 抖动的风险——这是传统范式下不存在的问题（每个 kernel 各自小而专）。

🧾
一句话总结这笔账

MegaKernel 用五样东西换一样东西：
用「每算子独立调优的自由 ＋ 现成 kernel 生态 ＋ 成熟 profiler ＋ 故障隔离 ＋ 编译简单」，
换「消掉全局 barrier，让依赖回到真实粒度」。

这笔交易在「小 batch、decode、小模型、新卡、低延迟」时划算，在别的场景不划算——这正是第十节那张判据表背后的道理，也解释了为什么它的加速比对着 vLLM 只有 1.0–1.7×，而不是数量级。

九、动态性：paged KV、变 batch 与在线请求

能不能上生产，看的是动态性怎么处理。一个静态编译出来的 megakernel，怎么应付随时到达、随时结束、长度各异的请求？

问题MPK 的做法
batch size 会变编译期为 2 的幂次 batch size 各生成一份 tGraph，运行时 scheduler 按当前 batch 选一份（和 CUDA Graph 按 batch 分桶捕获同思路）
continuous batching在 tGraph 的 start event 上，scheduler 做三件事：踢掉已完成的请求 → 纳入新到的请求 → 更新每请求 KV 元数据

十、在 vLLM 上落地：现状与三条路

10.1 先说结论：官方集成路线目前是断的

vLLM RFC #22201 提议把 MPK 做成 vLLM 的实验性执行后端，设计相当完整：

  • 走 Dynamo backend 机制，CompilationConfig.backend = "mirage"；
  • 分两层：兼容层在 vLLM 里（把 vLLM custom op 翻译成 Mirage high-level op），编译后端在 mirage 包里——两边可独立演进；
  • attention 特殊处理：做一个 Mirage 专用 attention backend，只产出 Mirage 能认的表示、不真的执行 attention，元数据用现有 metadata builder 填进静态 buffer；
  • 不需要 CUDA Graph capture（反正就一个 kernel），不支持的算子 fallback 回 fx.Graph 或 Inductor。

而 benchmark/benchmark_serving.py 的用法注释直接写着「停掉 MPK、起 vLLM、跑同一套 benchmark」——它把 vLLM 当对照组，而不是宿主。

10.3 三条可选路线

路线 A

复活 RFC 的 torch.compile 后端

按两层设计做：vLLM 侧写兼容层，backend="mirage"。难点在 attention——vLLM V1 的 attention 走自己的 backend + metadata builder，要么把输入完整 trace 进 fx.Graph，要么编译期手工传 buffer。工作量最大，最正统。

路线 B · 推荐

侧挂分流

不动 vLLM 内核，按流量特征分流：低延迟、小 batch、小模型走 MPK 的 OpenAI 兼容 server；高吞吐、长 prefill、复杂调度走 vLLM。上层加个 router。两边都是 OpenAI 协议，接起来几乎零成本。

路线 C

先把 vLLM 已有的手段开满

full CUDA graph capture、FlashInfer backend、算子融合 pass、关掉 enforce-eager。这些能吃掉税 1 的大部分。但税 2、税 3 是 vLLM 架构上吃不掉的——那才是 MPK 的独占领地。

10.4 什么场景 MPK 才真的有收益

这是判断要不要投入的核心，别搞反：

维度MPK 收益大MPK 收益小甚至为负
batch size小 batch / batch=1大 batch（GPU 本就吃饱，固定开销被摊薄到看不见）
阶段decode（memory-bound）prefill（compute-bound，已贴着算力上限）
模型规模小模型（0.6B–8B）超大模型（单 kernel 耗时长，固定开销占比小）
GPU 代次越新越好（B200 > H100 > A100）老卡
并行TP 多卡（通信重叠是独占优势，8×H100 上 1.1–1.4×）单卡
目标低延迟（TPOT / 交互式）高吞吐（throughput per GPU）
⚠️
别拿错数字去立项

README 首页那句 “reduces LLM inference latency by 1.2× to 6.7×” 是 2025-06 首发时的说法，对照组更宽泛（含 PyTorch + CUDA Graphs，那条线上确实有 ~10×）。

要和 vLLM / SGLang 比，请用论文里的 1.0–1.7×。注意区间下沿是 1.0×——即某些配置下没有收益。

10.5 实际风险

  • 模型要手工搭图。看 demo/qwen3/demo.py——权重映射表、每层的 grid_dim 都得手填，里面甚至有这样的注释：An add-hoc workaround for linear kernel ... will output unexpected result (not same output for same prompt) if the OUTPUT_SIZE is too big。它不是 vLLM 那种「HF 权重丢进去就能跑」的成熟度。
  • 算子覆盖是白名单制。TaskType 里没有的东西就没有，新架构要手写 CUDA task。
  • 参数手工调。num_workers / num_schedulers / grid_dim 填错就是性能悬崖或直接跑不起来。
  • 生态缺口。prefix caching、chunked prefill、结构化输出、LoRA 多路复用、P/D 分离……vLLM 有的这些，MPK 侧要么刚起步，要么没有。

十一、总结

层次结论
物理decode 是 memory-bound，算术强度只有 ridge point 的 1%，唯一瓶颈是 HBM 带宽。所有优化的本质是「别让带宽闲着」。Tensor Core 快 16 倍这件事，在 decode 阶段几乎用不上。
范式病根kernel 是调度与同步的最小单位 → 293 次 launch ＋ 293 次全局屏障 ＋ 依赖粒度过粗无法重叠。CUDA Graph 只治了第一条。
MPK 解法把调度单位从 kernel 下沉到 task（= 一个 SM 上的一个 CTA），用常驻 megakernel ＋ 片上 worker/scheduler 运行时 ＋ event 原子计数器自管依赖。三笔税一起消，scheduler 自身只占 0.28%。
vLLM 落地官方 RFC 已关闭，MPK 转向自建 OpenAI 兼容 server。现在想用走路线 B（侧挂分流）最务实；想做深则复活路线 A。收益 1.0–1.7×，只在小 batch / decode / 小模型 / 新卡 / 低延迟目标上成立。
MegaKernel 不是「把 kernel 写得更快」，而是把「kernel」这个抽象本身拆掉——让依赖回到它本来的粒度。
